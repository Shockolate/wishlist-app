# Operations

Running Hanker once it's live. Setup lives in [deployment.md](deployment.md); this is what to check, how often, and where to go when something breaks.

## Before inviting people widely

Do these once, and again after a big change to how the site runs.

- [ ] Better Stack's three monitors are green, and the backup heartbeat has reported ([Monitoring](deployment.md#monitoring)).
- [ ] A Better Stack test alert reaches your email (each monitor's menu → "Send test alert").
- [ ] A Sentry test event arrives with its token redacted ([Sentry → Check it works](deployment.md#check-it-works)). The API's wiring is proven by its tests and by its first real error; there's no safe way to force a production `500`.
- [ ] The restore drill has passed against a real nightly dump ([Restore drill and recovery](deployment.md#restore-drill-and-recovery)). It first passed on 2026-10-20.
- [ ] The runbooks in deployment.md match what you see in each dashboard.

## When something breaks

| You see                                                                               | Start here                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Someone says a share or manage page answered "Too many requests"                      | Vercel → `wishlist-web` → Firewall: the "Share and manage pages per IP" rule (D103). That's Vercel's `429`, not the app's. If real visitors on one IP are hitting it, raise `limit` in `infra/vercel.tf`                                                                                                                                                                                                                                                |
| Better Stack: Live or Site down                                                       | Vercel's status, then the latest deploy; roll back if it caused it ([Rollback](deployment.md#rollback))                                                                                                                                                                                                                                                                                                                                                 |
| Neon compute climbing fast, or a flood of requests on `/s/` or `/c/`                  | Vercel → `wishlist-web` → Firewall: the "Share and manage pages per IP" rule's traffic (D103). If it can't hold, switch on **Attack Challenge Mode** there for an hour: Better Stack will report false downtime and link previews may break until it's off. It stays a dashboard switch, not code                                                                                                                                                       |
| Better Stack: Deep down, Live up                                                      | Neon: its status page and the compute quota ([Monitoring](deployment.md#monitoring))                                                                                                                                                                                                                                                                                                                                                                    |
| Better Stack: backup heartbeat failed or missed                                       | [Backups → When it fails](deployment.md#when-it-fails)                                                                                                                                                                                                                                                                                                                                                                                                  |
| Better Stack: daily cron heartbeat failed or missed                                   | Vercel → `wishlist-api` → Settings → Cron Jobs: did it run? Its log has the counts or the error, and Sentry has the error by `requestId`. Press **Run** once fixed. Missed with no run at all means Vercel skipped it; a `cron heartbeat failed` warning in Sentry means the ping, not the cleanup, failed ([Daily cron](deployment.md#daily-cron))                                                                                                     |
| A Sentry issue                                                                        | Its `requestId` tag matches the API's `x-request-id` and Vercel's logs, which keep only an hour                                                                                                                                                                                                                                                                                                                                                         |
| A Sentry warning "Bright Data refused an Amazon lookup with status …"                 | The key, account or dataset is wrong: `401` a bad key, `400` often an inactive or out-of-credit account, `404` the dataset. Check Bright Data's dashboard, then [Turning on Amazon lookups](deployment.md#turning-on-amazon-lookups) to replace the key                                                                                                                                                                                                 |
| `unfurl LOOKUP_UNAVAILABLE … provider=amazon` in the API's logs                       | Bright Data is down or the month's credits are spent (Bright Data → Billing). Amazon links fall back to typing the details in until it recovers or the 1st                                                                                                                                                                                                                                                                                              |
| A Sentry warning "Etsy refused a listing lookup with status …"                        | The key or the request is wrong: `401` a missing key, `403` a refused or revoked one (check "Apps You've Made"), `400` a malformed request. See [Turning on Etsy lookups](deployment.md#turning-on-etsy-lookups) to replace the key                                                                                                                                                                                                                     |
| `unfurl LOOKUP_UNAVAILABLE … provider=etsy` in the API's logs                         | Etsy is down, or the app passed its 5 a second or 5,000 a day (`status=429`). Etsy links fall back to typing the details in until it recovers or the day resets                                                                                                                                                                                                                                                                                         |
| `tag-suggest UNAVAILABLE status=429` in the API's logs                                | Workers AI's daily allowance is spent (error `3036`). Suggestions stop until 00:00 UTC; nothing else is affected. `5xx` or no status is an outage on Cloudflare's side, which also clears itself                                                                                                                                                                                                                                                        |
| `tag-suggest TIMEOUT` or `tag-suggest BAD_ANSWER` in the API's logs                   | `TIMEOUT`: Workers AI took over 5 seconds, so the owner saw no suggestions. `BAD_ANSWER`: it answered something that isn't `{"tags": [...]}`. A few are normal; a steady run means the model changed, so check Cloudflare's changelog for the model in `tag-suggester.ts`                                                                                                                                                                               |
| A Sentry warning "Workers AI answered …"                                              | The token, account or model needs attention: `401` a bad token, `403` a token without Workers AI Read and Edit or the wrong account, `404` or `400` a retired model. See [Turning on tag suggestions](deployment.md#turning-on-tag-suggestions) to replace the token                                                                                                                                                                                    |
| Vercel: a certificate error on `hanker.dev`                                           | `dig +short CAA hanker.dev` still allows `letsencrypt.org`; https://letsdebug.net ([DNSSEC and CAA](deployment.md#dnssec-and-caa))                                                                                                                                                                                                                                                                                                                      |
| `hanker.dev` doesn't resolve for some people (SERVFAIL)                               | DNSSEC: https://dnsviz.net/d/hanker.dev/dnssec/ ([DNSSEC and CAA](deployment.md#dnssec-and-caa))                                                                                                                                                                                                                                                                                                                                                        |
| Bad data, newer than 6 hours                                                          | Neon point-in-time restore ([Rollback](deployment.md#rollback))                                                                                                                                                                                                                                                                                                                                                                                         |
| Bad data, older than 6 hours                                                          | [Restore drill and recovery](deployment.md#restore-drill-and-recovery), the "Real recovery" paragraph                                                                                                                                                                                                                                                                                                                                                   |
| A deploy run failed                                                                   | Its first red job's log; a stale-commit refusal from `assert-main-tip.sh` is by design ([Continuous deployment](deployment.md#continuous-deployment)); a red `sourcemaps` job alone means the browser maps are missing for that release, not that the release failed ([Sentry](deployment.md#sentry))                                                                                                                                                   |
| Infra drift: `infrastructure drift`                                                   | The run's summary shows what differs. A dashboard change nobody codified: apply `main` (`tofu-hanker apply`) to undo it, or codify it in a PR.                                                                                                                                                                                                                                                                                                          |
| Infra drift or an `infra-plan` run: `could not plan`, or `401`/`403` in the plan step | The Plan step's log names the cause. A `401` or `403`: a plan token expired, was revoked or lost a permission (the error names the provider); make a replacement with the same scopes and `gh secret set` it in both `infra-plan` and `infra-drift` ([Credentials](#credentials)). A failed `cloudflare_r2_bucket_lifecycle` or `_lock` postcondition: a backup rule was loosened; restore it in the dashboard first ([Backups](deployment.md#backups)) |
