# Wishlist App: Plan Roadmap

**Spec:** [`docs/superpowers/specs/2026-10-07-wishlist-app-design.md`](../specs/2026-10-07-wishlist-app-design.md)

The spec is delivered as five sequential plans. **Each plan is written only after the previous one has merged**, so it builds on the code that actually exists and on the spike results, not on guesses. This applies in particular to three findings from Plan 1:

- the merge method for stacked PRs,
- which header carries the real client IP through the Next.js rewrite,
- how preview aliases work.

Every plan ends with software that is deployed and tested on its own.

| # | Plan | Spec sections | Ships | Status |
|---|---|---|---|---|
| 1 | [Walking skeleton & delivery pipeline](2026-10-07-plan-1-walking-skeleton.md) | §3, §10, §11, §12 | Monorepo; contracts; NestJS API with problem+json, request IDs, rate limiter and a database-aware health check; Next.js web behind the `/api` rewrite; CI; per-PR previews with Neon branches; production deploys on merge; repository protections; spikes A–C | Done |
| 2 | Accounts & auth | §2 Actors, §5 Auth, §6.1–6.6, §6.9, §7 auth routes | Domain and DNS; Resend; signup, verify, login, logout, reset, change password, delete account; database sessions; CSRF guard; rate limits wired to endpoints; Turnstile; HIBP; CSP; daily cleanup cron; Mailpit-backed E2E | Not started |
| 3 | Owner wishlist | §2 Wishlist/Items, §5 Owner, §6.8, §7 `/list` and `/settings` | Wishlist and items CRUD; full-list reorder; best-effort unfurl with SSRF hardening; editor and settings UI; visual direction via the `frontend-design` skill | Not started |
| 4 | Sharing & claims | §2 Claims/Spoilers/Share link, §5 Public, §5.1, §6.3, §6.7 | Share page; claim flow; claim manage page; spoiler projection; transactional claim concurrency; token-in-URL protections | Not started |
